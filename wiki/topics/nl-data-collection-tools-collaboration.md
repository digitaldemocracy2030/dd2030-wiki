[[広聴AI]]・[[いどばた]]・[[倍速会議]]・farbrain/divcon などは「多くの人から自然言語データを集める」という目的を共有するが、アーキテクチャは根本的に違う。2026年8月、これらを一本化すべきか、どう協働するかが議論され、「統合ではなく、共通目的を持つ独立プロジェクト群として並置し、相互理解を進める」という方向が確認された。

## 背景 — なぜこの議論が起きたか

2026年8月の全体定例で、ボードメンバーの鈴木健が「各プロジェクトごとに戦略会議をやろう」と提案した（広聴AI・いどばた・Polimoney ごとに、9月以降にMeetでボードメンバーがサポートしつつ1年の方向性を話す）。これに対し、いどばたPMをぶるーも（Shutaro Aoyama）から引き継いだ kuboon が「各プロジェクト別ではなく、**横断的な雑談ミーティング**がほしい。各プロジェクトのビジョンが未だ不明確で、似たゴールをバラバラに目指している印象がある」と問題提起したことで、`#2_いどばたボット` で議論が始まった。

## 論点1 — 目的は共通、アーキテクチャは別

西尾泰和の整理:

- [[広聴AI]]と[[いどばた]]は「多くの人から自然言語のデータを集める手法」という意味で**目的に共通部分がある**が、**ソースコードの観点ではアーキテクチャが根本的に違うので一本化すべきでない**。
- この「目的が共通」は広聴AIといどばただけでなく、ぶるーも（Shutaro Aoyama）の[[倍速会議]]、tokoroten（中山心太）の farbrain / divcon も同様（さらに Jigsaw SenseMaker などのロングコンテキスト系ツールもこの系譜）。
- したがって、まずこのメンツで集まる「[[広聴AI]]×[[いどばた]] 合同ミーティング」が有益。会議前に各人が Google Docs に考えを書き出しておく（口頭より事前記述を好む人が多いという想定）。

鈴木健は「西尾に一旦リードしてもらうのがよさそう」と応じ、西尾がファシリテーターとなった。

## 論点2 — なぜコードでなく「継続」と「参加」に価値を置くか

西尾がまとめドキュメントで言語化した、一本化しない理由の思想的な根:

- **Coding Agent の進歩でソースコードを生み出すコストが激減**しており、コードベースの継続性の価値は低い（[[広聴AI]]の基盤にした Talk to the City も、同名で全く別のコードベースを mono-repo にしていた例がある）。
- 相対的に希少なのは「こういうきっかけで開発が始まり今に至る」という**プロジェクト継続の価値**と、「大勢が貢献した」という**参加の価値**。これが「dd2030の旗のもとに集まることで個人が活動するだけより大きな価値を生む」ことにつながる。
- この考えから広聴AIには**プラグインシステム**を入れ、「コンポーネント間インターフェイスの明確化」「部品の交換可能性」を持たせ、状況に応じて部分的に交換できるようにしている。
- 2026年8月時点、「何を作るべきか」は探索の余地が大きく、**個人がプロトタイプを作ることの価値が大きい**。この探索を妨げないことと、dd2030の相乗効果とを両立させたい。

## 論点3 — 手法の使い分け（embedding vs long-context）

- Talk to the City / 広聴AI が基盤にする「vector embedding してからクラスタリング」は**大規模データにはそれしかできない**が、**小規模データなら全部 long-context なフラグシップLLMのコンテキストに入れるアプローチ**（Jigsaw SenseMaker 等）の方が一般人に理解しやすい結果が出る。手法に固執すべきでない。
- ほとんどの自治体はデータ収集がボトルネック。
- 一方「無償で動いてほしい」「データ送信できない」など最新AIを使えない制約下では、embedding ベースの手法の価値が残る。その意味で tokoroten の「Local LLM / ブラウザで動く」方向は良い進化。

## いどばた側の現状整理（kuboon）

- ぶるーもから引き継いだ時は「既存いどばたは discon してリニューアル」という話だった。
- 「いどばたビジョン」「いどばた政策」の中途半端な合流計画を解消し、**明確に別プロジェクトとして整理**。
- チームみらいとの共同管理で責任者不明だったサーバは、先方担当と話して解消。
- 2つは本団体管理下でデモサーバを立ててもよいのでは（Cloudflareアカウントが欲しい）。
- 自分がゼロから考え直した「**いどばたボット**」（任意サイトにアドオンでき、貼られたページ内容を情報ソースに対話的に意見を聞き出し、自前DBに集約して類似意見をまとめる構想）は提案したが反応がなく放置されている。
- 「広聴AIといどばたのコンセプトの違いを明確にしないと新プロジェクトとして進めにくい」。

その後、事前まとめドキュメント上で西尾の「いま何が行動の妨げになっているか」という問いに答える形で、kuboon 自身が認識を更新した:

- 着想時は coding agent が今ほど進歩していなかった。現状から考えると、**情報が閉じた自己完結的サービスは各自治体が自分で作ればよく、こちらで作って提供する意味がない**。いどばたボットはこれに該当するので**もはや作る意義がない気がしている**。その方向なら skill 的なテキスト（AI利用のありがちな落とし穴など）を提供する方がよいのでは。
- 今なお価値があるのは**自治体横断的なシステム**: 個々の自治体単独では作れないもの、情報をやり取りする共通プロトコル・フォーマット、市民のサインイン基盤（これは割と欲しい）。

## 各メンバーからの回答（事前まとめドキュメント、2026-09-08取得時点）

西尾が各人に差し込んだ質問への回答が集まった。詳細は [[sources/kouchou-idobata-joint-meeting-prep|広聴AI×いどばた 合同ミーティング 事前まとめ]] を参照。

**ぶるーも（Shutaro Aoyama）**:

- 立場上も実態も[[多元現実]]社の実務にはほぼ関わっていない。[[倍速会議]]=[[Cartographer]]をプロダクトとして今後どう扱うかは高木に聞いてほしいが、最近の会話の感触ではプロダクトとして磨き込んでいくつもりはあまりなさそう。
- いどばたに関して具体的なアクションは浮かんでいない。引き継ぎについては「一年前に中途半端な状態でボールをパスしたまま関わりを落とした」ことを謝罪しつつ、「何を短期ゴールにすべきか・何を資産として引き継ぐと価値があるのか、当時も今も見えていない」と率直に記述。

**tokoroten（中山心太）**:

- **広聴AIをペライチのHTML化**した [kouchou-ai-serverless](https://tokoroten.github.io/kouchou-ai-serverless/) を公開。OpenAI API Key を設定画面から差し込むだけで動き、Chrome 内蔵の Gemini Nano を使えば無料で動作する。
- divcon は long-context を試したくて作ったデモで継続予定なし。farbrain はサーバクローズ済みでビジネス化に至らず。
- **ブラウザ版を広聴AIの本流とするのが良いのでは**という意見。西尾も「ライトなユーザにはインストールのトラブルがなくなる」と同意。

**ohki（Shingo OHKI）** — 論点の追加提起:

- dd2030 のプロダクトは開発者が利用現場の当事者とは限らず、一般的なOSSで暗黙に行われる**ユーザー価値の探索が抜け落ちやすい**。技術探索（プロトタイピング）自体には価値があるが、それだけで「次に何を作るか」は見えてこない。
- 「次に何を作るか」をMTGで決めるやり方自体が dd2030 に合っているのか。企業のプロダクト組織とも一般OSSとも違う、**dd2030 なりの「何を作るかの見つけ方」**を考えるべきでは。
- 現場との継続的関わりには窓口・責任主体・契約・守秘・データ管理の課題があり、深く関わるほど共有できない情報が増える。共有判断に迷うものは共有しない方に倒れやすかった。
- OSSゆえに誰がどこで使っているか把握しづらい。「使ったら実際どうだったかヒアリングさせてね」を最初から付けておく案。
