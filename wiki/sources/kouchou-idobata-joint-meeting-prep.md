# 広聴AI×いどばた 合同ミーティング 事前まとめ

- 元ファイル: `raw/minutes/2026-08-16_kouchou-idobata-joint-meeting-prep.txt`
- 元ドキュメント: [Google Docs](https://docs.google.com/document/d/1Wl5xCUkv2U8MkhW8-wLWr5TuLcDIpY2SFAnneKYL6Rk/)（継続更新される共同編集文書。本ページは2026-09-08取得時点の内容）
- 副題: 「目的の共通性と『一本化しない』協働のかたち」（2026-08-16〜）

## 何のための文書か

[[広聴AI]]・[[いどばた]]・[[倍速会議]]・farbrain/divcon など「多くの人から自然言語データを集める」ツール群の開発者が、合同ミーティングに先立って各自の世界観と進みたい方向を書き出した共同編集ドキュメント。目的は「個人の探索的プロトタイピングを妨げずに dd2030 として協働する形を探る」こと。合意形成ではなく相互理解が狙い。経緯と論点の全体像は [[topics/nl-data-collection-tools-collaboration|自然言語データ収集ツールの関係と「一本化しない」協働]] を参照。

Polimoney（自然言語データを集めるものではない）と[[コアループ]]（「ループを閉じる」ことが目的でより上位）は今回のスコープ外と明記されている。

## 各メンバーの記述の要点

### nishio（西尾泰和）

- Coding Agent の進歩でソースコードを生み出すコストが激減しており、コードベースの継続性の価値は低い。希少なのは「プロジェクト継続による価値」と「参加による価値」。
- この考えから広聴AIにプラグインシステム（インターフェイス明確化・部品の交換可能性）を導入中。
- embedding＋クラスタリングは大規模データ向け。小規模データは long-context なフラグシップLLMに全部入れる方（Jigsaw SenseMaker 等）が一般人に理解しやすい結果が出る。手法に固執すべきでない。ただし「無償で動いてほしい」「データ送信できない」制約下では embedding ベースの価値が残る。

### kuboon

- 「いどばたビジョン」「いどばた政策」のデモサーバを立てる案（Cloudflareアカウントが欲しい）。
- 構想していた「いどばたボット」（任意サイトにアドオンできるチャットボットで対話的に意見を聞き出し、自前DBに集約する）は、coding agent が進歩した現状では「情報が閉じた自己完結的サービスは各自治体が自分で作ればよい」ため**もはや作る意義がない気がしている**と自己評価を更新。その方向なら skill 的なテキスト（AI利用のありがちな落とし穴など）を提供する方がよいのでは。
- 今なお価値があるのは**自治体横断的なシステム**: 個々の自治体単独では作れない、情報をやり取りする共通プロトコル・フォーマット、市民のサインイン基盤（これは割と欲しい）。

### bluemo（ぶるーも / Shutaro Aoyama）

- 立場上も実態も[[多元現実]]社の実務にはほぼ関わっていない。倍速会議=[[Cartographer]]をプロダクトとして今後どう扱うかは高木に聞いてほしいが、最近の会話の感触では**プロダクトとしてガツガツ磨いていくつもりはあまりなさそう**。
- いどばたに関して具体的なアクションは浮かんでいない。
- いどばたの引き継ぎについて: 一年前に中途半端な状態でボールをパスしたまま関わりを落としたことへの謝罪と、「何を短期ゴールにすべきか・何を資産として引き継ぐことに価値があるのか、当時も今も見えていない」という率直な現状認識。

### tokoroten（中山心太）

- **広聴AIをペライチのHTMLにした**（[kouchou-ai-serverless](https://tokoroten.github.io/kouchou-ai-serverless/)）。設定画面から OpenAI API Key を差し込むだけで動く。Chrome 内蔵の Gemini Nano でも動くようにしたので、それを使えば無料で動作する。
- divcon: long-context を自分でも試したくて作ったデモで、続ける予定はなし。
- farbrain: 一時期サービス運用したが現在サーバクローズ。ビジネス化には至らず。
- ブラウザ版広聴AIについて「**これを広聴AIの本流とするのが良いんじゃないか**」という意見。西尾も「ライトなユーザにはインストールのトラブルがなくなるのでこの方向性が良い」と同意。

### ohki（Shingo OHKI）

「話したい論点とは少し違うかもしれないが」と断りつつ、**技術探索とユーザー価値探索の乖離**を提起:

- 一般的なOSSは開発者自身がユーザーであることが多く、技術探索とユーザー価値の探索が一緒に進む。しかし dd2030 のプロダクトでは開発者が利用現場の当事者とは限らず、同じ感覚で進めると**ユーザー価値の探索が抜け落ちやすい**。
- 現場では「一つを解決すると前後に別の課題が見えてくる」ことが多く、ヒアリングすれば「何を作るか」が分かるほど単純ではない。過程にいることで分かることが多い。
- 「次に何を作るか」をMTGで決めるやり方自体が dd2030 に合っているのか。企業のプロダクト組織とも一般的なOSSとも違う、**dd2030 なりの「何を作るかの見つけ方」**を考えられるとよいのでは。
- 現場との継続的関わりには窓口・責任主体・契約・守秘・データ管理の課題があり、今の dd2030 の形では難しい。自身は dd2030 とは別の形で現場との取り組みを試している。深く関わるほど守秘義務から共有できない情報が増え、共有判断に迷うものは共有しない方に倒れやすかった。
- OSSゆえに誰がどこで使っているか把握しづらく、自治体の広報発表で初めて利用を知ることも多い。「使ったら実際どうだったかヒアリングさせてね」を最初から付けておいてもいいのかも。
